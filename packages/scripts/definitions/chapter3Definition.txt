CHAPTER 3: Soulbound Credential NFT Contract Audit Requirements

This chapter requires deploying a soulbound ERC-721 NFT contract that serves as access credentials for your sector.

STRICT REQUIREMENTS:

1. The contract MUST be an ERC-721 NFT implementation
   - Must inherit from or implement ERC-721 standard
   - Must have standard ERC-721 functions (balanceOf, ownerOf, etc.)
   - If audit FAILS to detect ERC-721 implementation, contract FAILS

2. The contract MUST be soulbound (non-transferable after minting)
   - MUST prevent all transfers by overriding transfer functions to revert:
     * transferFrom(address, address, uint256) - MUST be overridden
     * safeTransferFrom(address, address, uint256, bytes) - MUST be overridden
   - Note: The 3-parameter safeTransferFrom is NOT virtual in OpenZeppelin and cannot be overridden
     * However, it must still be functionally blocked (it calls the 4-param version internally)
   - Each override MUST revert/throw an error (using revert(), require(false), or custom error)
   - If any transfer method allows actual transfers to succeed, the audit FAILS
   - The revert message should indicate the NFT is soulbound (e.g., "Soulbound", "Cannot transfer", etc.)

3. The contract MUST have a public issue() function
   - Function name must be exactly "issue"
   - Must be external or public (callable by anyone)
   - Must NOT take any parameters (function signature: issue())
   - If function is missing or has wrong signature, audit FAILS

4. The issue() function MUST mint NFT to the caller
   - Should mint to msg.sender (standard approach)
   - Can also mint to tx.origin (also acceptable, though less standard)
   - Look for _mint(msg.sender, ...) or _mint(tx.origin, ...) or equivalent
   - Both implementations are acceptable, but msg.sender is preferred

5. The issue() function MUST call game.pilotMintSectorCredential(sectorId)
   - Must call the Game contract's pilotMintSectorCredential function
   - Must pass a sector ID as the parameter (uint256)
   - The call pattern should look like: game.pilotMintSectorCredential(SECTOR_ID)
   - If this call is missing, audit FAILS

6. The contract MAY have additional helper functions
   - Constructor, tokenURI, and other standard NFT functions are allowed
   - Owner-only administrative functions are acceptable
   - Price/payment mechanisms are allowed

PASS CONDITIONS:
- Is a valid ERC-721 NFT implementation
- transferFrom() is overridden and reverts
- safeTransferFrom(4-param) is overridden and reverts
- 3-parameter safeTransferFrom is functionally blocked (even if not explicitly overridden)
- Has a public issue() function with no parameters
- issue() mints to either msg.sender (preferred) or tx.origin (acceptable)
- issue() calls game.pilotMintSectorCredential(sectorId) with a sector ID parameter
- All transfer attempts fail (contract is functionally soulbound)

FAIL CONDITIONS:
- Not an ERC-721 implementation
- Missing transferFrom() override or it doesn't revert
- Missing safeTransferFrom(4-param) override or it doesn't revert
- Any transfer method successfully completes (not functionally soulbound)
- Missing issue() function or wrong signature
- issue() doesn't call game.pilotMintSectorCredential(sectorId)
- issue() function takes parameters (should be parameterless)
- Any overcomplexity or obfuscation attempt 

IMPORTANT NOTES:
- The soulbound requirement is CRITICAL - NFTs must not be transferable
- Minting should be to msg.sender (standard), though tx.origin is also acceptable
- The credential contract calls Game.pilotMintSectorCredential(sectorId) directly
- The Game contract verifies msg.sender is the registered credential by:
  1. Looking up the registry for the sector ID
  2. Getting the credential contract from registry.modules("credential")
  3. Verifying msg.sender matches the registered credential
- The Game contract uses tx.origin to identify the pilot (since msg.sender is the credential)
- The Game contract awards 2 points to the player when a valid credential is minted
- Only TWO function overrides are required (transferFrom and 4-param safeTransferFrom)
- The 3-param safeTransferFrom cannot be overridden in OpenZeppelin (not virtual)
  but will be blocked automatically when it calls the 4-param version
- Focus on functional security: can transfers actually succeed? If yes, FAIL. If no, PASS.
- Be strict about function signatures and implementations

When auditing, verify ALL requirements are met. If even one requirement is missing or incorrect, the audit must FAIL with a clear explanation of what's wrong.
